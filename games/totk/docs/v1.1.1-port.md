# Tears of the Kingdom 1.1.1 on this fork

This fork is **upstream MacNativeGames/main plus one feature: Tears of the Kingdom 1.1.1 support**. Everything
else is byte-for-byte upstream, including Breath of the Wild 1.6.0/1.9.0 and the Switch 2 games (Donkey Kong
Bananza, Pokemon Pokopia). The 1.1.1 support exists because the player wants 1.1.1 (1.1.2 introduced gameplay
regressions), while upstream removed 1.1.2 support on 2026-11-02 and never carried 1.1.1.

Nothing here may be sent upstream. This document is the hand-over record: what the port adds, how it was
verified, how to rebuild it, and **how to take a future upstream update without losing it**.

## 8. Features upstream gates to 1.2.1 / 1.4.3 — ported to 1.1.1 (2026-11-06)

Upstream gates several TOTK features to the update versions. The full inventory, and what 1.1.1 got:

**Ported to 1.1.1** (gates opened; the machinery itself is version-independent — heap overlays, shader-level SSAO, size-based output modes):

- **Scene-follows-canvas** (was 1.2.1+): the scene renders at the canvas size (a 1080p canvas renders a 1080p scene, 2K a 2K one) instead of the game's own 1600×900, with the matching `-scene-<w>x<h>` HeapDef overlays. Runtime gate `TARGET_OS_OSX && defined(TOTK_GAME_V121)` now also takes `defined(TOTK_GAME_V111)`; the builder makes the scene overlays for v111 (`make_output_res_overlay.py --scene`, `build_app.py` step list); `TOTK_RENDER_RES` unset takes the canvas size.
- **Native 4K output** (was 1.2.1/1.4.3): a 3840×2160 swapchain and heap overlay, `--native-4k` / `--no-native-4k` (default on a Mac with ≥16 GB), the settings-panel 4K row, `TOTK_OUTPUT_RES=3840x2160`. The runtime side was already size-based (`runtime_output_modes` sets the 4K bit when the swapchain is 4K); only the builder's version gates opened.
- **Stronger ambient occlusion (SSAO)** (was 1.4.3/1.9.0/1.2.1): the settings-panel row (off / 150 / 200 / 300 %, a hand-written percent kept), `ssao.txt`, `TOTK_SSAO`. The graphics layer patches the shaders as they load and is version-independent; `SETTINGS_SSAO` now also compiles for v111.

Already 1.1.1's since the first port (same session family): the 60 fps patch, real time, the cloth/hair clock, the cursor/aim speed veneers, the texture-pool offset widening, the ultrawide aspect stubs, the benchmark camera, cloud saves, mods, 2K output, MetalFX output stage, the settings panel.

**Analyzed and deliberately NOT ported:**

- **The >60 FPS fade fix** (#466 #556 #538, 1.4.3 only): it clamps `trunc(2.1 × ratio30)` to ≥ 1 at four byte-counter sites (`ldrb`/`add`/`strb`, counter ÷ 20). Exhaustive scans of 1.1.1's and 1.2.1's mains find **zero** byte-counter increments, **zero** ÷20 divisions and **zero** fcvtzs+add+strb shapes: the 1.1.x builds implement the distance/LOD fades with word counters and comparisons instead. Porting would mean inventing a mechanism, not moving one — left to 1.4.3.
- **Native 5K** (1.4.3, needs ≥32 GB): same machinery as 4K scaled; the app's memory default checks the same RAM, so it works if asked with `--native-5k` once RAM allows, but it stays off by default on 1.1.1 as it is upstream-wise on 1.2.1 (the gate is 1.4.3-only by design).
- **VR** (1.4.3): needs a Quest headset and the zeldaVR launcher; the runtime is shared but untestable here, and the build gate stays 1.4.3.
- **The effects page** (1.4.3: LOD / render-distance / FOV / shadow-resolution / depth-of-field knobs + `TOTK_LOD_SCALE` etc.): its five patch sites exist only in 1.4.3's main (1.4.3 has a new compiler and 1.2.1 has none of them either); each needs its own disassembly research in 1.1.1's main. Not portable as a block; do it per-knob if wanted, with the runtime's instruction-word guards as the correctness gate.
- **AA-method row, pt-BR text** (1.4.3's RomFS text), **HDR frontend** (1.4.3), **frame-step pin** (1.4.3's frame-controller layout): each needs 1.4.3-only data or a different main layout; left as they are.

Verify the build carries them with: the app log shows `bigger output (TOTK_OUTPUT_RES=auto): a 3840x2160 swapchain` and `scene render size <w>x<h>, follows the canvas` when built with `--native-4k`; the settings panel shows the 4K row and the ambient-occlusion row on 1.1.1.

## 2. Where the 1.1.1 port's working data lives

All of it is in the work tree (all git-ignored except the expected-hashes file):

- `extracted/v111/` – decrypted 1.1.1 update (exefs modules, RomFS index), made once.
- `rewritten/v111/` – the rewritten modules the loader patches at runtime.
- `analysis/v111-port/phase12-validation.json` – the validation report the scripts assert against.
- `build/totk-native-v111` – the compiled game binary (rebuilt by `make`; the app bundles a copy).
- The app's shader cache lives outside the repo: `~/Library/Application Support/MacNativeGames/TOTK/shader-cache/`.

Provenance of the addresses: `scripts/map_version_sites.py --from v121 --to v111` mapped every site from 1.2.1 to
1.1.1's main (a different build, so every site moved; the original instruction words are unchanged). The
slow-motion bounce check site (`0xce3fec`, now `0xbea414`) was found by its three-instruction shape, unique in
1.1.1. Every patch verifies the original instruction word at runtime and refuses to start on a mismatch, so a
wrong address fails loudly at boot, never silently corrupts the game.

## 4. Building the player's app

```bash
cd ~/Documents/Nintendo/MacNativeGames
.venv/bin/python build_app.py \
  "/Users/admin/Documents/Nintendo/TOTK roms/The Legend of Zelda Tears of the Kingdom [0100F2C0115B6000][v0].nsp" \
  --update "/Users/admin/Documents/Nintendo/TOTK roms/The Legend of Zelda Tears of the Kingdom [0100F2C0115B6000][v196608].nsp" \
  -k "/Users/admin/Documents/Nintendo/Keys-22.1.0/prod.keys" \
  --shared-fonts games/totk/extracted/firmware/shared-fonts \
  --work "/Users/admin/Documents/Nintendo/TOTK_build.noindex" \
  -o "/Users/admin/Documents/Nintendo/Tears of the Kingdom 1.1.1.app"
```

The game NSP and the 1.1.1 update NSP (v196608) are the player's own files; never commit them, the keys, the
firmware, or any extracted/rewritten game content. `--work` reuses the extraction cache, keep it.

The player's settings (config C, realtime + 60 fps + cloth clock, 1440p output) are launch-time flags, not
build flags. MetalFX upscale (key 3 / `TOTK_MFX_UPSCALE`) is **off** by default: Apple's `MTLFXSpatialScaler`
produces green square tiles on the title-screen glow lines; leave it off unless the picture is compared
first. The game's own FSR-style upscale is used instead.

### Shader caches

- The per-binary shader chain lives at `~/Library/Application Support/MacNativeGames/TOTK/shader-cache/rt-…`,
  keyed by the translation chain and the seed's context hash. **A rebuild with the same seed keeps the same
  chain**: the ~1 000 warm variants and the Metal pipeline archives carry over, and the next boot is fast.
- The first ever boot of a fresh install compiles the world shaders once (~10 minutes of background
  translation at the title screen, then the load is quick). Do not delete the chain dir.
- Building with Xcode + the Metal toolchain (`xcodebuild -downloadComponent MetalToolchain`) makes
  `step_shader_libs` bundle pre-compiled `.metallib`s in the app, so even a fresh install boots without the
  compile pass. Optional: without it the runtime translates as described above. This Mac has no Xcode
  installed; the toolchain weighs 13+5 GB, which is why it was skipped.

## 5. zeldaVR must be a real directory

Upstream tracks `games/totk/zeldaVR` as a symlink to the root `zeldaVR` project. Its sources contain
`#include "../../third_party/d2r_gfx/gfx/nvn/fps_overlay.h"`, written as if zeldaVR sits *inside*
`games/totk`. macOS clang resolves the symlink before applying `..`, so the symlinked layout cannot compile.
This fork therefore keeps a real copy of the project at `games/totk/zeldaVR` (the root project is untouched).
If a future update re-creates the symlink, replace it with the copy again.

## 6. Updating the fork to a newer upstream main

The fork must stay "upstream + the 1.1.1 patch", so the update is a **re-apply**, never a merge of the old
fork's history (that is how the earlier attempt at this port turned into a 1 100-line slimming of upstream:
BotW/NS2 build targets, VR, `GAME_INFO`, scene-follows-canvas, heap overlays, `pchtxt.h` and more were
dropped and had to be re-added by hand).

Procedure for the next session (branch names: upstream remote `upstream`, the fork remote `fork`):

```bash
cd ~/Documents/Nintendo/MacNativeGames
git fetch upstream
git checkout -B totk-1.1.1-port upstream/main      # start from the new upstream tip
```

Then re-apply §1's table onto that tree, in this order (the anchors are the version keys they sit next to,
so `grep -n v121` finds the new locations if upstream moved anything):

1. `git checkout totk-1.1.1-port -- games/totk/assets/expected-v1.1.1.json` (pure data; the old
   `totk-1.1.1-clean2` branch is superseded — do not port from it, it drifted).
2. `runtime/game_version.h`: insert the `#elif defined(TOTK_GAME_V111)` block before
   `#elif defined(TOTK_GAME_V121)`. If upstream added a new version block, keep their order and put v111
   beside v121.
3. `runtime/game_patches.c`: five insertions, each an `#elif defined(TOTK_GAME_V111)` (cloth table, cursor
   sites, pool-offset sites, benchmark sites, aspect sites) plus the guard widenings
   `#if defined(TOTK_GAME_V121)` → `#if defined(TOTK_GAME_V121) || defined(TOTK_GAME_V111)` in
   `patch_cursor_speed`, `patch_bench_cam` and `runtime_game_patches`. If upstream changes those functions,
   port the *meaning* (1.1.1's own site addresses) rather than the text diff.
4. `build_app.py`: `UPDATED111` + `VERSIONS`/`UPDATES` include `v111`. If upstream adds a new game version
   to its own tuples, leave their entries alone and only add `v111`.
5. `Makefile`: the `v111` `GAME_DATA` eval + `runtime-v111`/`binary-v111` targets (copy whatever the newest
   upstream `*-v121` rule looks like then).
6. The scripts: add `v111` to every version-choice list where `v121` appears (the table above is the list).
7. `games/totk/zeldaVR`: real directory, not the symlink (§5).

Conflict cues, and what they mean:

- A conflict in `game_version.h` or `game_patches.c` almost always means upstream **changed a shared table's
  shape** (a new patch kind). Port 1.1.1's entry into the new shape; do not resolve by deleting the other
  versions' rows.
- A conflict in the verify scripts is upstream adding a version: keep their list, add `v111`.
- `patch_sites.py` fails ("unresolved") if a `GAME_ADDR` the 1.1.1 block needs went missing upstream: add it
  to the v111 block (mapped from the same logical address with `map_version_sites.py --from v121 --to v111`).
- `prepare_runtime.py`'s 1.1.1 hash assert pins the exact 1.1.1 main image. If it fires, the update NSP on
  disk is not the expected build.

Verify after the re-apply, then build the app (§4). Keep the shader-cache rules: the rebuild keeps the warm
chain when the seed is unchanged, so the player's next boot is fast.

## 7. Player-side flags (config C, for the record)

`TOTK_REALTIME` (on by default), `TOTK_FPS60` (on by default), `TOTK_CLOTH_REALTIME` (on by default),
1440p output via the settings panel / `TOTK_OUTPUT_RES=2560x1440`. Cloud saves: the iCloud folder
`~/Library/Mobile Documents/com~apple~CloudDocs/Nintendo` (chosen in the app); sync happens at start, a few
seconds after a save commit, and at quit. `TOTK_CLOUD_SAVE_DIR` overrides, `=0` disables.
