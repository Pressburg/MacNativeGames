# The night of 2026-10-22: what was done, and how to do it again without the mess

This file is the handover for the work of 2026-10-22 on this branch, written after the night left a pile of
test builds behind. It says what was done, what the working recipe is, and what to do differently next time.
Nothing in it needs the game files to read; the commands are the ones that were actually run.

**The code is still there**: the branch `feature/overnight` holds the whole night (the mod path, nine upstream
issues and PRs, the settings window, the mod manager, the presentation modes) and is pushed to `origin`. This
file lives on that branch as well as on `feature/frame-rate-only`, the branch that is *only* the original code
with the 60 fps / refresh rate work on top.

---

## 1. What the night did

### The mod path (the main goal)

`games/totk/scripts/mod_exefs.py` merges a mod's code patches into the retail `main` before the Apple silicon
rewrite. Four things were changed in it:

| Before | After | Why |
| --- | --- | --- |
| a `.pchtxt` that names another build **stopped the build** | it is left out with a note, and the build goes on with the patch that fits | the mod managers ship one file per game version, so a mod folder normally holds several; a build must not die on the ones that are not for this version |
| an `.ips` was only read as a main patch when it was named `main` or the 16/20-byte build id | the Atmosphere form (the build id zero-padded to the 32 bytes of an NCA build id) is read too | that is how the community ships the triple-buffering and the 60 fps patches |
| a mod with only `romfs/` was an error | it is accepted ("skipped"): there is no code to merge, and the data half is loaded at run time | most mods are data only |
| the refusal named the first overlapping site | it names every site | a player wants to know which feature of theirs is in the way |

And a real bug was found: **`@stop` ended the pchtxt file, so only its first section was applied.** A community
mod may ship several sections in one file (theboy181's "Visual Improvements" holds the depth-of-field removal
and the lens-flare removal in one), and the second one was silently dropped. `@stop` now ends the *section*; a
line after it without a new `@enabled` is still ignored, so nothing that was applied before changes. The same
reading is in the runtime's own `TOTK_PCHTXT` reader (`runtime/game_patches.c`), which is the reference the
build-time reader follows.

### The mod catalogue

`docs/mod-catalogue.md` lists every mod that was tried: exefs or romfs, the format, the game version, what the
build did with it, and whether the app was built and the game run with it. It is the file to read before touching
the mod path again. The three mods the owner named are answered there:

- **LOD** is a code patch (`pchtxt`): "LOD Improvement" (the TOTK Optimizer's own) merges and runs; the separate
  "Increased LOD" mod for 1.4.3 merges and **stops the game** (see §4).
- **FOG** is data: Serfrost's Defogger replaces the environment and cave palette packs. It runs alone.
- **NX Optimizer** is a desktop app whose payload is UltraCam, a code injection: it adds `exefs/main.npdm` and a
  `subsdk3` module. The app loads main, sdk and subsdk0 and loads nothing at run time, so an injected module
  never runs. That is not fixable in the mod path; it would need a module loader in the app.

### Upstream issues and PRs

Nine were taken (the whole list with the commits and how each was checked is in `state/ledger.md`): PR #191 (the
Switch Pro HID gyro calibration), #167 (the iOS seed build), #144 (by3's mod manifest script), #166 (the
pipeline prediction), #185 (the CPU texel region copy), #197 (the PlayStation button icons), #199 (a card image
that also holds its update), #160 (the iOS app icon), #149 (rumble over HID).

### The frame rate work (`feature/frame-rate-only`)

The presentation modes came from another session of the same night: `TOTK_PRESENT_MODE=uncapped|display|game`
(and `locked`) picks how the frames are paced, the frame rate follows the screen the game is on (not the main
display), the link's rate is no longer clamped to 30..120, and the frame's tick accounting follows the display
link instead of a fixed 60 Hz (issue #118). That branch is the original code plus those commits, and it is what
the app below was built from.

## 2. The working recipe

### Build the app

```bash
cd ~/Documents/Nintendo/MacNativeGames
python3.14 build_app.py \
  "$HOME/Documents/Nintendo/TOTK roms/The Legend of Zelda Tears of the Kingdom [0100F2C0115B6000][v0].nsp" \
  -k "$HOME/Documents/Nintendo/Keys-22.1.0/prod.keys" \
  --update "$HOME/Documents/Nintendo/TOTK roms/The Legend of Zelda Tears of the Kingdom v1.2.1[0100F2C0115B6800][v393216].nsp" \
  --firmware "$HOME/Documents/Nintendo/Firmware" \
  --work "$HOME/Documents/Nintendo/TOTK_build" \
  -o "$HOME/Documents/Nintendo/Tears of the Kingdom.app"
```

- **`--work` matters.** Without it the build puts its work folder *next to the game file*
  (`~/Documents/Nintendo/TOTK roms/TOTK_build`) and starts from zero: the 17 GB RomFS is extracted again and the
  startup shaders are translated again. Point it at one work folder and keep it; the second build of the same
  version is minutes.
- The build takes ~8 minutes with a warm work folder (1.2.1), ~17 minutes for a version it has not seen (1.4.3).
  The last 6-7 minutes are the Metal warm-up (the startup shaders are compiled for this Mac); without a Metal
  toolchain (`xcodebuild -downloadComponent MetalToolchain`) the build says so and the shaders are compiled in
  the background at the first start instead.
- `--out`/`-o`: build to a new path, check it, and only then replace the app you use. The build writes a
  `.partial` folder and renames it at the end, so a failed build never leaves a half app behind.

### Install a code mod (exefs)

A mod folder is `<mod>/exefs/` (the code patches) and/or `<mod>/romfs/` (the data files):

```bash
python3.14 build_app.py <the same command> --mod ~/path/to/the/mod --install-mod-romfs
```

- The code patches are merged into the retail `main` **before** the rewrite, and the app is bound to the merged
  module by hash. The retail ExeFS is never touched.
- A `.pchtxt` must name the build it was made for (`@nsobid-<build id>`); one that names another build is left
  out with a note, so a mod that ships a file per version works on every version.
- An `.ips` / `.ips32` is read as a main patch only when its name says so: `main`, or the build id (the 16- or
  20-byte form, or the 32-byte zero-padded Atmosphere form).
- A patch that lands where the app or the rewrite patches itself is **refused**, with the address and the name
  of the site. That is not a bug: those sites are the app's own features (the 60 fps patch, the output
  resolution, the aspect ratio).
- Mods that only inject a module (`subsdk3`, `subsdk9`) are noted and skipped: the app loads main, sdk and
  subsdk0 and nothing else.

### Install a data mod (romfs)

```bash
MODDIR="$HOME/Library/Application Support/MacNativeGames/TOTK/mods/v121"   # the version folder
rsync -a --exclude='.DS_Store' --exclude='manifest.tsv' "<mod>/romfs/" "$MODDIR/"
python3.14 games/totk/scripts/make_mod_manifest.py "$MODDIR" --app "<the app>" --version v121
```

The manifest names every file, its size, its SHA-256 and the original's; the game checks them at start, so a mod
made for another version stops the start instead of loading. Check it worked:

```bash
grep "mods/v121 checked" ~/Library/Logs/MacNativeGames/totk.log | tail -1
```

### Run the game unattended

```bash
open -a "$HOME/Documents/Nintendo/Tears of the Kingdom.app"
# later:
grep -E "上屏节奏|游戏帧工作时间" ~/Library/Logs/MacNativeGames/totk.log | tail -2
```

## 3. The mistakes to avoid (they cost the night)

1. **The display sleeps after two minutes** (`pmset -g custom` says `displaysleep 2`), and then the game stops at
   start with `FAIL: native display link initialization`: `CVDisplayLinkCreateWithActiveCGDisplays` needs an
   active display. `caffeinate -dimsu` keeps the machine awake but does **not** wake a display that already went
   to sleep. `caffeinate -u -t 30` wakes it for the run - do that right before the launch.
2. **A run that ends with a signal leaves no "exit" line** in
   `~/Library/Application Support/MacNativeGames/TOTK/game-slot/history.log`. The launcher reads the last run as a
   crash, opens the settings window instead of the game, and waits for a click that never comes. Write the line
   back by hand, or delete the stale `holder` file in the same folder when a crashed run left one.
3. **The game slot is shared.** One game at a time on the Mac: a second build's app waits for the first to exit
   ("等待游戏位置"). Two agents running games in the same night will trip over each other - use different work
   folders and check who is running.
4. **One working tree, two agents.** A second session (the owner's desktop app) worked the same branch in the same
   working tree. It ran `git stash` + `git reset --hard` in the middle of the night and lost four hours of edits,
   and it committed work it found in the tree under its own messages. **Use a separate worktree or a separate
   branch per agent, and commit every unit** - a stash is not a backup.
5. **The build's work folder is shared state**: a second build overwrites `extracted/<version>/mod-exefs.json` and
   `logs/mod-exefs-<version>.log`, so the evidence of one build disappears when the next one runs. Copy the log
   and the report out of the work folder right after the build.
6. **A pchtxt that replaces an `adrp` breaks the code it belongs to.** The game's address stays in the register
   and the game reads or writes through it. The build-time merge is survivable (the rewrite repairs the sequence
   and drops the patch - so the mod silently does nothing), but applied at run time (`TOTK_PCHTXT`) the same
   patch stops the game. Two community mods hit this: the lens-flare removal and the 1.4.3 "Increased LOD".
7. **A `.pchtxt` may hold several sections.** Read `@stop` as the end of a section, not of the file, or half of
   the mod is dropped without a word (that was the bug of the night).

## 4. What to do better next time

- **One work folder per agent, one branch per agent, and a commit after every unit.** The night's biggest loss
  was the `git stash` from a second session.
- **Do the destructive experiments on a copy.** The crash isolation of the night (one app per case, ~7 minutes
  per build) needed 15 app bundles and 203 GB. The same questions can be answered with the *merged module* alone:
  `mod_exefs.py apply` writes the merged `main`, and `patch_nso.py` writes the rewritten one - the two files are
  enough to see what the rewrite did to a patch, without a build.
- **Check the patch's shape before merging it**: if the bytes it replaces are an `adrp` / `adr` (or the
  instruction after them uses that register), the patch will break the code. The build can check this and refuse
  the patch with a clear message; that check does not exist yet.
- **Say what a mod does, not just that it merged.** The lens-flare patch merges, builds and runs, and does
  nothing. A build that compared the merged module with the rewritten one and reported the patches the rewrite
  dropped would have said so.
- **The map cursor is still frame-counted.** Above 60 fps the game's own UI (the map cursor is the known case)
  moves faster than on the console. The `game` presentation mode hides it; the real fix is to make the game's UI
  count seconds. The main module has no symbol table here, so the site has to be found by reading 40 MB of ARM64 -
  that needs a day, not a night.
- **The iOS build and the Breath of the Wild build were never made** (no iPhoneOS SDK, no BOTW game files on
  this machine). A data-only mod now builds for BOTW; its code half is still refused, because BOTW 1.6.0's patch
  sites are not listed in `scripts/patch_sites.py`.
- **The picture with a mod on was never compared against the picture without one.** Every run of the night was
  unattended, so the window was never in front and the game never got past the title screen. Someone has to play
  the thing.
